# Object Storage

Wire S3-compatible object storage into the backend for file uploads — profile
pictures, documents, or any user-uploaded content.

Locally, `floci` (an S3-compatible emulator) is already in `compose.yaml` under the
`--profile floci` flag. In production the same code points at real S3 by swapping
env vars. No code changes required between environments.

The upload pattern avoids routing file bytes through the Go server: the frontend
requests a presigned URL from the backend, uploads the file directly to S3, and
hands the resulting object key back to the app. The backend never touches the bytes.

```
Frontend         Backend          S3 / floci
   |                |                 |
   |-- POST /upload/request --------> |
   |                |-- presign PUT ->|
   |<-- { url, key }                  |
   |                                  |
   |-- PUT <bytes> ------------------>|
   |                                  |
   |  (store key however app needs)   |
```

---

## 1. Environment variables

Add the following to `.env.example`. For local dev, `AWS_ENDPOINT` points at the
floci container. Leave it empty or unset when targeting real S3.

```
AWS_ENDPOINT=
AWS_REGION=
AWS_BUCKET=
AWS_ACCESS_KEY_ID=
AWS_SECRET_ACCESS_KEY=
```

---

## 2. Storage config

Create `internal/config/storage.go` following the pattern in
`internal/config/database.go`. Load the five vars above and fail fast at startup
if any required one is missing.

Add the new config to `internal/config/config.go` so it is available on the
`Configuration` struct alongside `App` and `Database`.

---

## 3. S3 client

Add the AWS SDK v2 to `go.mod`:

```
github.com/aws/aws-sdk-go-v2
github.com/aws/aws-sdk-go-v2/config
github.com/aws/aws-sdk-go-v2/service/s3
```

Construct the client from the storage config. When `AWS_ENDPOINT` is set, point
the client at it (this is what makes floci work locally). Pass the client into the
server wiring the same way `*sql.DB` is passed today.

---

## 4. `StorageService`

Create `internal/services/storage.go` following the pattern in
`internal/services/character.go`. Define the interface and a concrete struct that
holds the S3 client and bucket name:

- `RequestUploadURL(ctx context.Context, key, contentType string) (string, error)` —
  returns a presigned PUT URL valid for a short window
- `RequestDownloadURL(ctx context.Context, key string) (string, error)` — returns a
  presigned GET URL
- `Delete(ctx context.Context, key string) error`

S3 logic belongs here, not in the controller.

---

## 5. Controller and route

Create `internal/controllers/storage.go` and `internal/server/routers/storage.go`
following the patterns in the existing `character` files.

Register `POST /api/v1/upload/request`. The request body takes a filename and
content type. The response returns a presigned upload URL and the object key the
caller must store.

Add `StorageService` to `types.ServiceParams` and pass it through `types.RouteParams`
so it reaches the router without changing every function signature.

---

## 6. Frontend — upload utility

Create a function (e.g. `frontend/src/api/upload.ts`) that:

1. Calls `POST /api/v1/upload/request` via the API client to get a presigned URL
   and object key
2. PUTs the file directly to the presigned URL using a plain `fetch` — this call
   goes to S3, not the backend, so the API client's auth header must not be attached
3. Returns the object key

---

## Local dev setup

Start the full stack including floci:

```sh
docker compose --profile floci up
```

The floci container exposes an S3-compatible API on port 4566. Set `AWS_ENDPOINT`
to its address in your `.env` file.

---

## Definition of done

- `POST /api/v1/upload/request` returns a presigned URL and object key
- A `PUT` to that URL with a file body succeeds against floci
- The download URL for the same key returns the uploaded content
- No file bytes pass through the Go server at any point
